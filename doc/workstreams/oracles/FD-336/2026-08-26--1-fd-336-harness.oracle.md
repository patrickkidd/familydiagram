# FD-336 — sandbox test harness oracle (Patrick, ratified in chat 2026-08-26)

Patrick's success picture, restated by the coordinator and confirmed with two amendments (dynamic backend port; deliberately non-happy-path mock data).

- H1. One harness, not one per ticket. A single standard sandbox harness. Every unit finds it the same way (named in the project instructions: one command, one doc) and uses it as-is. No unit writes its own sandbox script; a ticket-named copy is a defect. Nothing else in the repos describes a launch recipe.
- H2. It stands up the whole system together, from the ticket's code. One command brings up a backend, a Pro app, and a Personal app, all against the same backend and database, each running the ticket's worktree code (falling back to the origin clone only when the ticket has no worktree for that repo, and saying so). The backend listens on a dynamically allocated free, unique port — the number is irrelevant to the caller. It never touches Patrick's 8888 server or his dev database.
- H3. Backend data is chosen per run: mocked or a duplicate of production. Mocked = seeded users, licenses, diagrams, discussions/statements/speakers, access rights — enough for any unit's journeys without a running app. LLMs under-generate non-happy-path data: the mocked seed MUST deliberately exemplify the non-happy paths (named hostile profiles: empty/single-token/last-name-only/unicode/very long names, duplicate names, self-referential bonds, dangling refs, empty and very large diagrams, shared read-only and read-write cases, another user's case, expired/missing licenses, users without a free diagram, discussions without a user, stale row versions, malformed staged data) alongside the happy family, plus a seeded random generator. Duplicate-production = the real production dump restored into a throwaway sandbox database on Patrick's machine, never committed, never the production or dev DB.
- H4. Robust. Repeatable up / reseed / down; isolated per instance (ports, DB, prefs, app data) so two units run at once; cleans up after itself; fails loudly (a hung health check, dead bridge, or missing dependency is a failure, not a silent success); never kills another instance's processes.
- H5. It is the validation surface for every unit going forward. Agent-run journeys and human journeys both run on it; it is maintained as product tooling — tested, documented in one place, kept in sync with the models it seeds.

Scope note: the production-data path is in this PR (restore of the existing dump into a throwaway local Postgres; no anonymizer — data stays on Patrick's machine as with the existing pull-to-dev flow).
